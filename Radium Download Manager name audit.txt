Radium Download Manager: Flux and OpenIDM Legacy Branding Audit
Audit date: 4 November 2026
Repository: https://github.com/sayedalve/Radium-Download-Manager
Branch: main
Inspected commit: 7b76e719b6bdb5f88ba4536e6426994566692d36
Audit mode: Read only. No repository files were changed.
1. Verdict
NOT CLEAN. The current product is branded Radium in its main executable names, browser manifest display names, extension UI and installer identity. The rebrand is nevertheless incomplete in active code, package scripts, browser storage, developer instructions and current documentation.

The most important problems are:
1. The portable release ZIP script can choose an old flux.exe or openidm.exe when the current Radium executable is missing, then copy it under the name radium.exe. It checks architecture, but does not verify the embedded product name or version.
2. The native messaging host can override the Radium IPC path with an old Flux or OpenIDM environment variable after the shared path helper has already selected the Radium path.
3. New remote torrent offers create files under %LOCALAPPDATA%\OpenIDM\tmp\torrents, even though the current application data directory is %LOCALAPPDATA%\Radium Download Manager.
4. The browser extension still writes its session state only under flux_* storage keys. The restore code mentions radium_* keys but does not request them from browser storage.
5. The active AI agent instructions still describe the project as OpenIDM and direct agents to old executable names, namespaces, temporary paths and IPC names.
6. The current developer and architecture documents contain many incorrect commands, paths, executable names and pipe names.
The legacy browser host IDs, data migration paths and POSIX encryption seed are not ordinary cleanup items. They have compatibility consequences and should not be removed as part of a global replacement.

4. Detailed findings
RDM-01. Release ZIP builder can package an old executable as Radium
Severity: High
Files: scripts/package-release-zip.ps1, tests/test_installer_smoke.py, tests/test_dist_portable.py

The package script prefers Radium binaries, but then searches legacy names:
- scripts/package-release-zip.ps1:68-73 searches radium.exe, then flux.exe and Flux.exe.
- scripts/package-release-zip.ps1:75-87 adds more legacy build and distribution paths.
- scripts/package-release-zip.ps1:101-114 does the same for flux-nmh.exe.
- scripts/package-release-zip.ps1:142-150 reports a missing executable only after all legacy fallbacks have been searched.
- scripts/package-release-zip.ps1:270-272 copies the selected file to radium.exe, Radium.exe and radium-nmh.exe in the package.
The validation checks CPU architecture. It does not verify the PE ProductName, FileDescription, internal version string, executable version resource or expected Radium build hash. A stale Flux binary of the correct architecture can therefore be renamed and distributed as Radium if the current binary is missing and an old file remains in a fallback location.

The test suite weakens this further. tests/test_installer_smoke.py:281-285 accepts a version output containing Flux as valid. The portable test also has a Flux.exe fallback in tests/test_dist_portable.py:15-19.

Impact: A release package could contain an old application under a Radium filename. The installer smoke test may accept it rather than fail the release.

Recommended action: For release packaging, fail closed when radium.exe or radium-nmh.exe is missing. Verify the embedded product name and version against the release version before packaging. If old executable compatibility is needed for a developer-only tool, make it an explicit opt-in mode that cannot be used by release CI. Change the smoke test to require Radium Download Manager and the expected version. Do not accept Flux as a valid current identity.

Compatibility risk: Low for production release packages. A developer who deliberately uses an old build path may need to update their local command. That is preferable to silently publishing an old executable.
RDM-02. Native messaging host can override the Radium IPC path
Severity: High
Files: src/common/ipc_path.hpp, src/nmh/main.cpp, integration tests

The shared helper correctly checks the current variable first:
- src/common/ipc_path.hpp:48-51 checks RADIUM_IPC_SOCKET, then FLUX_IPC_SOCKET, then OPENIDM_IPC_SOCKET.
- src/common/ipc_path.hpp:55-67 then creates a pipe named Radium_IPC_<SID> on Windows or /tmp/radium_ipc_<uid>.sock on POSIX.
However, src/nmh/main.cpp:238-241 calls the helper and then independently overwrites its result when FLUX_IPC_SOCKET or OPENIDM_IPC_SOCKET is present. It does not check RADIUM_IPC_SOCKET in this second step.

This creates a precedence bug. When both the current Radium variable and an old variable exist with different values, the native messaging host selects the old value. The desktop app uses the helper's Radium first behavior, so the host and desktop can connect to different IPC endpoints.

The current integration tests do not expose the bug because tests/run_all_integration_tests.py:702-704 and tests/test_repair_pipeline_e2e.py:735-737 set all three variables to the same value.

Impact: Browser to desktop communication may fail on machines or launch environments that retain an old environment variable with a different value.

Recommended action: Remove the second environment lookup from src/nmh/main.cpp and use the shared helper as the single source of truth. Add a regression test that sets all three variables to different paths and asserts that RADIUM_IPC_SOCKET wins.

Compatibility risk: Preserve the legacy variables as lower priority fallbacks in the shared helper. Do not delete them until old scripts no longer depend on them.
RDM-03. Active agent instructions still define the product as OpenIDM
Severity: High
File: AGENTS.md

This file identifies itself as the active governance policy for AI coding agents, but its instructions remain based on OpenIDM:
- Lines 1-4 describe the project objective as maintaining OpenIDM and name openidm.exe and openidm-nmh.exe.
- Line 60 directs developers to use openidm:: namespaces.
- Lines 90-92 specify %LOCALAPPDATA%\OpenIDM\tmp and OpenIDM_IPC.
- Other sections describe old module and executable paths.
This is not a historical archive. It is an active file that coding agents are told to read before every task.

Impact: Future automated code changes can reintroduce old product naming, old storage paths and outdated architecture. It can also cause developers to follow instructions that do not match the current repository.

Recommended action: Rewrite AGENTS.md against the current main implementation. Use Radium names, current CMake targets, current namespaces if those are retained, actual directory paths and actual browser host names. Mark migration aliases as compatibility interfaces in a separate section. Do not use OpenIDM as the current project identity.

Compatibility risk: None for the application. This is developer guidance, not a runtime contract.
RDM-04. Current CMake targets do not match documented build commands
Severity: High for developer workflow
Files: CMakeLists.txt, docs/DEVELOPMENT_SETUP.md, docs/WINDOWS_BUILD_AND_PACKAGING.md, audit/RADIUM_REBRANDING_REPORT.md

The current CMakeLists.txt defines these application targets:
- radium
- radium-nmh
- radium_unit_tests
- radium_core_tests
- N_m3u8DL-RE
It does not define flux, flux-nmh, flux_unit_tests, openidm or openidm-nmh targets. No add_executable(flux...) target is present in the inspected CMake configuration.

Yet docs/DEVELOPMENT_SETUP.md:54-57 tells developers to build flux flux-nmh flux_unit_tests. docs/WINDOWS_BUILD_AND_PACKAGING.md:16-17 claims the Radium targets have Flux and OpenIDM aliases. audit/RADIUM_REBRANDING_REPORT.md also claims compatibility targets are maintained.

Impact: Following the development guide can fail because the named CMake targets do not exist. The rebranding report overstates the presence of build compatibility aliases.

Recommended action: Update development instructions to use current targets. If a compatibility target is genuinely required, define it in CMake and test it. Otherwise remove the alias claim from current documentation. Do not describe old executable filenames as CMake targets unless they are actually built.

Compatibility risk: Low. Existing scripts that invoke old CMake target names will need to change, but the current CMake file already does not provide those targets.
RDM-05. New torrent metadata is written into the old OpenIDM directory
Severity: Medium
File: src/ui/win32_main_window.cpp

The current Radium application creates remote torrent metadata under:

%LOCALAPPDATA%\OpenIDM\tmp\torrents\<GUID>\metainfo.torrent

Evidence:
- FetchTorrentMetainfo starts at line 3504.
- The old root is constructed around lines 3525-3530 as local_app_data / L"OpenIDM" / L"tmp" / L"torrents".
- metainfo.torrent is written around lines 3548-3558.
- When the fetch completes, the UI records the task directory in task.part_path at line 9791 so task removal can clean it.
This is an active write path for new Radium torrent offers, not a read-only legacy lookup.

Impact: New Radium work creates an OpenIDM directory on the user's machine. It splits temporary data between the Radium data directory and an old product directory. Task cleanup exists, but an abrupt process termination can leave temporary data in the old location.

Recommended action: Store this data under the configured Radium temporary root, preferably ControllerConfig::temp_root_dir, rather than a literal product path. Keep a cleanup routine for abandoned directories under the old OpenIDM path during migration.

Compatibility risk: Medium. Existing unfinished torrent tasks may still point to old paths in persisted task state. Before moving or deleting old directories, migrate or continue to honor those stored paths.
RDM-06. Browser extension still uses Flux keys as its only persisted session keys
Severity: Medium
File: extension/js/background.js

The current code does not yet make Radium keys canonical:
- Lines 119-126 write only flux_cacheData, flux_disabledHosts, flux_tabUrls, flux_recentClicks, flux_recentResponses, flux_redirectChains and flux_reverseRedirects.
- Lines 134-141 ask browser storage for only the flux_* keys.
- Lines 143 onward check data.radium_* || data.flux_*, but the Radium keys were not requested from storage.
The rebranding report says Radium keys are saved while Flux keys are mirrored for compatibility. That is not what the current implementation does. The old Flux keys remain the sole persisted representation in this code path.

Impact: The current extension still writes state under the old namespace. If a future cleanup removes those keys without a migration, browser session state such as cached media, disabled hosts, recent click correlation and redirect correlation may be lost.

Recommended action: Make Radium keys the primary stored keys. Read both Radium and Flux keys during migration. When only old keys exist, copy or migrate them to Radium keys. Keep dual reads for at least one compatibility period. Update tests to verify both fresh Radium storage and upgrade from Flux storage.

Compatibility risk: High if the old keys are deleted before migration. Treat these as persistent user data, not harmless variable names.
RDM-07. Active stream errors still show Flux to users
Severity: Medium
File: src/engine_stream/nm3u8dl_re_adapter.cpp

Examples include:
- Around line 1126: Stream uses unsupported DRM protection (...). Flux does not circumvent DRM.
- Around line 1768: Please refresh the URL in Flux to resume.
- Around line 3279: Stream uses unsupported DRM protection. Flux does not circumvent DRM.
These are active error strings returned by the stream pipeline. They are not historical comments.

Impact: Users can see the old product name in error dialogs or status details even though the application is Radium.

Recommended action: Replace the displayed brand with Radium or use neutral wording such as This application does not circumvent DRM. Keep error codes unchanged.

Compatibility risk: Low. Error strings may be asserted by tests or scripts, so search the test suite before changing exact text. Preserve the error codes.
RDM-08. Active network requests still identify themselves as Flux
Severity: Medium
Files: src/crawler/site_grabber.cpp, src/engine_torrent/torrent_parser.cpp, src/engine_ftp/ftp_client.hpp

Current strings:
- src/crawler/site_grabber.cpp:215 sends User-Agent: ... FluxDownloadManager/1.0 when fetching crawled pages.
- src/engine_torrent/torrent_parser.cpp:122 sends User-Agent: Flux/0.3.0 when downloading a remote torrent file.
- src/engine_ftp/ftp_client.hpp:28 uses anonymous@flux.org as the default anonymous FTP password.
These values can be sent to external servers. The FTP value is a protocol default, not an authentication secret, but it still carries a stale contact identity.

Impact: Remote servers and logs can identify the client as Flux or as version 0.3.0. The FTP anonymous contact value is outdated.

Recommended action: Use a consistent Radium user agent with the current version. For anonymous FTP, use a neutral documented value or a configurable contact value. Do not invent or use an unverified email domain.

Compatibility risk: Low. Some servers may log or filter user agents, so test crawler and torrent retrieval after changing them.
RDM-09. CMake still treats Flux version macros as the primary interface
Severity: Medium
Files: CMakeLists.txt, src/common/version.hpp, src/ui/win32_main_window.hpp

CMakeLists.txt:4-9 defines only FLUX_VERSION_MAJOR, FLUX_VERSION_MINOR, FLUX_VERSION_PATCH and FLUX_VERSION_STRING from PROJECT_VERSION.

src/common/version.hpp:29-45 defines Flux macros as aliases to Radium macros when they are not already defined. But CMake defines the Flux macros first, so the build still uses the old names as the primary version definitions.

src/ui/win32_main_window.hpp:322 uses FLUX_VERSION_STRING for the About dialog version.

src/app/main.cpp prints RADIUM_FULL_VERSION_STRING, but that macro has a hard-coded 1.0.0 fallback in version.hpp. The current project version is also 1.0.0, so this is not a current displayed version error. It can become one when the CMake project version is bumped without updating the fallback.

Impact: The source of truth for version values is split between old macros and Radium macros. A future version bump can make the CLI full version string stale while the About dialog uses the CMake version.

Recommended action: Define RADIUM_VERSION_* in CMake from PROJECT_VERSION. Keep FLUX_VERSION_* as deprecated aliases in the header if external build scripts still need them. Update the About dialog to use the Radium macro. Generate RADIUM_FULL_VERSION_STRING from the project version instead of hard-coding 1.0.0.

Compatibility risk: Low if the old macros remain aliases for at least one compatibility period.
RDM-10. Native messaging diagnostic checks the wrong pipe name
Severity: Medium
File: scripts/diagnose-native-messaging.ps1
- Around line 160, $expectedPipeName is set to Flux_IPC_$userSid.
- The current pipe helper creates Radium_IPC_<SID> in src/common/ipc_path.hpp.
- The diagnostic scans active pipes for Radium or old names, but then compares the result against the Flux pipe name.
A live Radium pipe can therefore be discovered but not accepted as the expected pipe. The script can report a warning even when Radium is listening correctly.

The same script still asks the user to find Flux Download Manager and look for [Flux Trace] messages around lines 299-302.

Impact: Support diagnostics can mislead the user and send troubleshooting in the wrong direction.

Recommended action: Check Radium_IPC_<SID> first. Optionally check old Flux and OpenIDM names as compatibility diagnostics, but report them separately. Update all user instructions and trace labels.

Compatibility risk: Low. This changes a diagnostic, not the runtime IPC protocol.
RDM-11. Installer smoke test accepts Flux output as a valid current build
Severity: Medium

Around lines 281-285, the smoke test chooses radium.exe if present, otherwise flux.exe, then accepts a version response containing Radium, Radium Download Manager or Flux.

This is too permissive for a release verification test. It can approve an old binary or a binary with old product identity as a Radium installation.

Recommended action: Require the exact current product name and expected version. Keep a separate compatibility test if old executable support is still intended. Do not let legacy branding satisfy the current release identity check.

RDM-12. Part file cleanup test does not match the current HTTP engine filename
Severity: Medium
Files: src/brisk_engine/http_download_engine.cpp, tests/run_all_integration_tests.py, docs/DATA_MODEL_AND_STORAGE.md

The current HTTP engine creates a partial file as:

<destination>/<filename>.<task_id>.part

Evidence: src/brisk_engine/http_download_engine.cpp around lines 550-560.

The integration test searches for:
- *.radium.part
- *.flux.part
- *.openidm.part
at tests/run_all_integration_tests.py:881-885.

None of these patterns matches <filename>.<task_id>.part. The test can pass while a real current-format partial file remains on disk.

The documentation also describes <filename>.openidm.part, which is not the current implementation.

Recommended action: Make the test derive the actual expected part_path from test task IDs or search for the actual *.part naming pattern in the controlled test directories. Update storage and recovery docs to describe the current path. Do not preserve a fake .radium.part extension merely to satisfy the test.

Compatibility risk: Low. Ensure the test only inspects test-owned directories so it does not delete user files.
RDM-13. Test matrix claims a migration test absent from current test source
Severity: Medium
Files: docs/TEST_MATRIX.md, tests/cpp/unit_tests.cpp

docs/TEST_MATRIX.md around line 15 lists TestFluxBrandingAndLegacyDataMigration as a passing C++ unit suite.

A repository search for that exact function name returned documentation and historical audit references, but no current test source. Recommended action: Plan a separate namespace and logging refactor. Rename the namespace and macros across source and tests in one compileable change. RDM-23. Windows DPAPI description contains OpenIDM, but the POSIX key seed must not be renamed
Severity: Low for the Windows description; Preserve the POSIX seed
File: src/common/crypto_utils.cpp

There are two different strings with very different consequences:
1. Around line 150, Windows CryptProtectData stores the description OpenIDM_Credential. The current CryptUnprotectData call passes nullptr for the returned description pointer. This label is metadata, not the DPAPI decryption key. It may be updated for branding after normal crypto tests.
2. Around line 37, POSIX DeriveUserLocalKey uses the seed OpenIDM_DPAPI_Equivalent_UserKey_v1_UID_ to derive the AES-256-GCM key. ProtectSecret and UnprotectSecret both use this derivation. Changing the seed changes the encryption key and makes already stored secrets fail authentication during decryption.
Recommended action: Keep the POSIX derivation seed unchanged unless a versioned credential migration is implemented. A safe migration would need to read old blobs with the old key, then re-encrypt them using a new versioned key and verify all records before discarding the old derivation. The DPAPI description can be changed separately, but it is low priority.

9. Current documentation: Correct branding specification, IPC, storage, release and architecture documents. Mark obsolete ADRs and dated records as historical or superseded.
10. Internal symbol cleanup: Rename openidm namespaces, logging macros and private WM_OPENIDM_* symbols as a separate source refactor.
11. Metrics schema cleanup: Rename primary benchmark and package metric keys to Radium while preserving old historical data or adding a schema migration.

## Section 3: Runtime and Installation Risks

### 1. Inconsistent Torrent Working Directory (Finding F-001)

In `src/ui/win32_main_window.cpp` (line 3530), the torrent metadata fetch directory is explicitly hardcoded:

```cpp
const std::filesystem::path torrent_root = std::filesystem::path(local_app_data) / L"OpenIDM" / L"tmp" / L"torrents";

```

When a user adds a torrent via magnet link or remote URL, Radium creates and writes files under `%LOCALAPPDATA%\OpenIDM\tmp\torrents`.

* **User Impact:** The application violates its advertised directory isolation (`%LOCALAPPDATA%\Radium Download Manager\`).
* **Uninstallation Risk:** The Radium uninstaller removes `%LOCALAPPDATA%\Radium Download Manager\` but leaves `%LOCALAPPDATA%\OpenIDM` on the user's disk, leaving residual files.

### 2. Pre-Rebrand Release Binaries in MSIX Package (Findings F-002, F-003, F-004)

Inspection of the compiled executables packaged inside `release/Radium-x64-1.0.0.0.msix` revealed that they were compiled on October 29, 2026—one day before the October 30 rebranding:

* `radium.exe` contains compiled string `\\.\pipe\Flux_IPC_` at offset `0x238270`.
* `radium-nmh.exe` contains compiled string `\\.\pipe\Flux_IPC_` at offset `0x90a8` and falls back to looking for `Flux.exe` (`0x9308`) and `flux.exe` (`0x9318`).
* `tools/win-x64/N_m3u8DL-RE.exe` outputs `N_m3u8DL-RE (Flux Stream Worker v0.3.0 / N_m3u8DL-RE v0.3.0-beta CLI contract)`.
* **Runtime Failure Risk:** If a user installs the MSIX package, the native host attempts to communicate over `\\.\pipe\Flux_IPC_<SID>`, whereas a newly compiled desktop process built from the updated source tree listens on `\\.\pipe\Radium_IPC_<SID>`. This leads to inter-process communication timeouts and broken browser download interception.

### 3. Temporary Muxing File Collisions (Findings F-005, F-006)

During video stream muxing in `src/engine_stream/nm3u8dl_re_adapter.cpp` (lines 1388 and 1914), intermediate files are created in the user's active download directory using the legacy patterns `<filename>.flux_mux` and `<filename>.flux_yt_mux.<ext>`. If a user monitors their download directory, these filenames are visible and confusing.

## Section 5: Compatibility Risks

A naive, global "search-and-replace" across the repository would cause severe regressions. The following identifiers require a disciplined migration strategy:

### 1. Windows DPAPI Credential Encryption Description

* **File & Lines:** `src/common/crypto_utils.cpp` lines 37 and 150.
* **Legacy Identifiers:** `L"OpenIDM_Credential"`, `"OpenIDM_DPAPI_Equivalent_UserKey_v1_UID_"`.
* **Risk:** In `CryptProtectData`, the description string is cryptographically bound into the output ciphertext blob. If changed unconditionally without a decryption fallback, users upgrading to Radium with stored HTTP proxy credentials, site logins, or private tracker passkeys in their existing SQLite database (`state.db`) will experience decryption failures.

### 2. Windows Named Pipe Endpoint Fallbacks

* **File & Lines:** `src/common/ipc_path.hpp` lines 48–52, `src/nmh/main.cpp` line 239.
* **Legacy Identifiers:** `FLUX_IPC_SOCKET`, `OPENIDM_IPC_SOCKET`.
* **Risk:** Automated regression suites, containerized test runners, and developer environments specify these environment variables to inject custom pipes. They must remain as fallbacks while prioritizing `RADIUM_IPC_SOCKET`.

### 3. Browser Extension Native Messaging Host Registrations

* **File & Lines:** `installer/radium.iss` lines 185–195, `scripts/register-native-messaging.ps1` lines 33–44.
* **Legacy Identifiers:** `com.flux.downloadmanager`, `org.openidm.native`.
* **Risk:** Existing users who have already installed the browser extension from the Chrome Web Store or Firefox Add-ons repository have manifests configured with `com.flux.downloadmanager`. If the installer stops writing the compatibility registry keys, existing browser extensions will immediately disconnect with `"Specified native messaging host not found"`.

### 4. YouTube Descriptor JSON Payload Tag

* **File & Lines:** `extension/catch-script/catch.js:295`, `extension/js/background.js:1677`, `src/core/download_controller.cpp:995`.
* **Legacy Identifier:** `fluxType: "YOUTUBE_STREAM"`.
* **Risk:** When media detection catches a YouTube stream, the JSON descriptor passed across the extension-to-app bridge includes `fluxType`. The desktop engine checks this field to invoke the specialized extractor. Removing `fluxType` before ensuring all worker binaries and extension versions are synchronized will break YouTube video downloads.

## Section 6: Intentionally Retained References

The following references are valid, deliberate, and **must not be removed**:

1. **Legacy Database & Profile Migration Routine (`src/common/path_sanitizer.cpp:621–675`):**
* Code inspects `%LOCALAPPDATA%\OpenIDM` and `%LOCALAPPDATA%\Flux Download Manager` to migrate `tasks.db` / `state.db` to `%LOCALAPPDATA%\Radium Download Manager\state.db`. Removing this code breaks upgrades for existing users.


2. **Inno Setup Single Instance Mutex (`installer/radium.iss:115`):**
* `AppMutex=Local\Radium_SingleInstance,Local\Flux_SingleInstance,Local\OpenIDM_SingleInstance`. Ensures the installer prompts users to close running instances of older versions prior to overwriting shared DLLs.


3. **Compatibility Native Host Manifests (`installer/manifests/`):**
* `com.flux.downloadmanager.chromium.json`, `org.openidm.native.chromium.json`, and their Firefox equivalents. Preserved to service legacy browser extension IDs.


4. **Offline Loopback Test Flags (`src/app/main.cpp:84`, `nm3u8dl_re_worker.cpp:400`):**
* `FLUX_ALLOW_LOOPBACK` and `OPENIDM_ALLOW_LOOPBACK`. Required to allow integration test suites to execute without opening external network ports.


5. **Extension Local Storage Fallback (`extension/js/background.js:120–141`):**
* Reading `data.radium_* || data.flux_*`. Ensures tabs open during extension updates do not lose active download capture state.


6. **Archived Engineering Audits (`docs/archive/maintenance-audits/` and `audit/`):**
* Historical records detailing past development phases. Modifying these would compromise audit integrity.

## Section 9: Final Verdict

### Verdict: **CRITICAL**

### Evidence & Justification:

While the repository outwardly appears to be rebranded as Radium Download Manager, this audit uncovered **critical operational and compatibility defects** that impact runtime execution and user data:

1. **Active User Data Isolation Violation:** `src/ui/win32_main_window.cpp` actively creates directories and writes torrent files to `%LOCALAPPDATA%\OpenIDM\tmp\torrents`, violating user data boundaries and leaving uncleaned orphaned files upon uninstallation.
2. **Shipped Binary Desynchronization:** The compiled binaries in `release/Radium-x64-1.0.0.0.msix` were generated prior to the socket rebranding. They listen and connect on `\\.\pipe\Flux_IPC_` and invoke `Flux Stream Worker v0.3.0`, introducing IPC disconnection risks when interacting with updated components.
3. **Direct User Exposure:** Multiple user-facing error dialogues in the stream download pipeline explicitly prompt the user to `"refresh the URL in Flux"` and warn that `"Flux does not circumvent DRM"`.
4. **Network Leakage:** Outbound HTTP crawlers, torrent parsers, and FTP engines actively identify as `FluxDownloadManager/1.0`, `Flux/0.3.0`, and `anonymous@flux.org`.
5. **Documentation & Screenshot Stale State:** The root `README.md` prominently displays screenshots showing legacy download paths (`\Downloads\Flux`), and primary developer guides (`AGENTS.md`, `CONTRIBUTING.md`) still instruct contributors to build `OpenIDM`.

Until Phase 1 and Phase 2 remediation items are addressed, the rebranding cannot be considered complete.
